# SCHEMA.md — Vault Metadata Schema

**Version:** 2.0.0
**Scope:** Frontmatter standards for all canonical notes in the business vault
**Authority:** Human founder + Curator
**Last reviewed:** 2026-05-19

---

## Design Principles

The schema is optimized for:

1. **Retrieval quality** — every field must improve search or context precision
2. **Low write amplification** — fields that require constant updates are eliminated
3. **Agent autonomy** — agents should be able to populate most fields without human input
4. **Long-term maintainability** — the schema must work at 100k notes without becoming a burden
5. **Minimal surface area** — fewer fields means fewer validation failures

Fields are included only if they serve at least one of: retrieval, governance, provenance, or lifecycle management.

## Frontmatter Specification

### Canonical Note (Layer 1)

This is the full schema for any note with `canonical: true`. All required fields must be present before promotion.

```yaml
---
# ── IDENTITY (immutable after creation) ───────────────────────────────
id: knw-YYYYMMDD-NNNNN

# ── CLASSIFICATION ─────────────────────────────────────────────────────
title: "Human-readable title"
type: concept | adr | sop | summary | decision | research | entity | knowledge | content
project: FounderOS | CinematicOS | IAMBrain | SlowEncodes | SocialMedia | global
domain: strategy | architecture | operations | product | content | infrastructure | finance

# ── RETRIEVAL ──────────────────────────────────────────────────────────
summary: "One sentence. Optimised for semantic search. Written as a declarative statement."
tags: [domain/strategy, type/adr, project/FounderOS]

# ── LIFECYCLE ──────────────────────────────────────────────────────────
status: refined | validated | promoted | archived
canonical: true
created: YYYY-MM-DD
updated: YYYY-MM-DD
schema_version: "2.0"

# ── QUALITY ────────────────────────────────────────────────────────────
canonicality: 3 | 4 | 5
confidence: high | medium | low

# ── PROVENANCE ─────────────────────────────────────────────────────────
source: URL | agent_name | meeting | import | human
agent: Brainstormer | Planner | Builder | Validator | Curator | human
distilled_from: "00_Inbox/Raw/YYYY-MM-DD-slug.md"

# ── RELATIONSHIPS ──────────────────────────────────────────────────────
superseded_by: ""
supersedes: ""
review_after: YYYY-MM-DD

# ── CONFLICT ───────────────────────────────────────────────────────────
contested: false
contradictions: []
---
```

## Required Fields

These fields are **required** on all canonical notes (`canonical: true`). Promotion is rejected if any are missing.

| Field | Description | Who sets it |
|---|---|---|
| `id` | Immutable identifier | Curator |
| `title` | Human-readable note title | Agent or human |
| `summary` | One-line retrieval summary | Agent or Curator |
| `type` | Note classification | Agent |
| `project` | Project scope | Agent |
| `status` | Lifecycle state | Curator |
| `canonical` | Must be `true` | Curator |
| `created` | ISO date of creation | Agent |
| `updated` | ISO date of last body modification | Curator |
| `canonicality` | Quality tier 1–5 | Curator |
| `confidence` | Claim confidence | Agent or Curator |
| `source` | Origin of the knowledge | Agent |
| `schema_version` | Schema version at time of creation | Curator |

---

## Optional Fields

These fields are set when relevant. They are not required for promotion.

| Field | Description | When to use |
|---|---|---|
| `domain` | Knowledge domain | When note is cross-project or needs domain indexing |
| `tags` | Namespaced taxonomy tags | Always useful; include when known |
| `agent` | Which agent wrote the note | When generated by a specific agent |
| `distilled_from` | Raw transcript source | When note was distilled from a transcript |
| `superseded_by` | ID of replacement note | When this note is deprecated |
| `supersedes` | ID of note this replaces | When replacing an older note |
| `review_after` | Date to re-evaluate the note | For time-sensitive knowledge (operational context: 30d, canonical: 180d) |
| `contested` | True if contradictions exist | Set by Curator when conflict is detected |
| `contradictions` | List of conflicting note IDs | Set by Curator |
| `ttl` | Expiry date for operational memory | Required for Layer 2 notes only |

## Removed Fields (and why)

The following fields from previous schema versions were removed:

| Removed field | Reason |
|---|---|
| `last_accessed` | Requires constant update on every retrieval; creates write amplification; not worth the staleness signal at current scale |
| `stage` | Duplicate of `status`. One lifecycle field is sufficient. |
| `relevance_score` | Subjective, becomes stale, requires manual maintenance. Relevance is better handled by retrieval ranking. |
| `content_hash` | Useful in theory; in practice adds complexity with minimal benefit at current scale. Git diff is sufficient for change detection. |
| `derived` | Relationship tracking via wikilinks is sufficient. A separate array creates maintenance burden. |
| `parent` | Same as `derived` — wikilinks handle this more naturally. |

These can be reintroduced at scale if a concrete need arises. Do not add them speculatively.

## ID Policy

### Format

```
knw-YYYYMMDD-NNNNN
```

Where:
- `YYYYMMDD` is the date the ID was assigned
- `NNNNN` is a zero-padded 5-digit monotonic sequence counter

Examples: `knw-20260513-00001`, `knw-20260519-00042`

### Generation Rules

1. The current counter value is stored in `09_System/id-counter.txt` as a plain integer
2. Before assigning any new ID, the Curator reads the counter, increments it, writes it back, and includes the file in the same Git commit as the new note
3. Counter is never decremented
4. Counter is never reset
5. If two promotions happen in the same day, the NNNNN sequence continues from where it left off

### Immutability Rules

1. Once assigned, an `id:` field is never changed — not on rename, move, merge, or archive
2. The pre-commit hook rejects any commit that modifies an existing `id:` field in a tracked file
3. When a note is superseded, the old note retains its ID; the new note gets a new ID; `superseded_by` links them

### Counter Script

```python
# scripts/next_id.py
import pathlib, datetime

counter_file = pathlib.Path("09_System/id-counter.txt")
current = int(counter_file.read_text().strip())
new_val = current + 1
counter_file.write_text(str(new_val))
date_str = datetime.date.today().strftime("%Y%m%d")
print(f"knw-{date_str}-{new_val:05d}")
```

## Lifecycle States

```
raw        → Unprocessed. Just created. No validation.
refined    → Metadata complete. Summary written. Segmented if needed.
validated  → Cross-referenced. Contradictions checked. Confidence assigned.
promoted   → canonical:true. In active index. Durable.
archived   → Superseded or deprecated. Excluded from indexes. Preserved in Git.
```

**State transition rules:**

| From | To | Requirements |
|---|---|---|
| raw | refined | All required fields present, summary written |
| refined | validated | Cross-references added, duplicates checked, confidence assigned |
| validated | promoted | No unresolved contradictions (or flagged), linked to related notes, indexed, `canonical: true` |
| any | archived | Superseded by newer note, or project closed, or explicit deprecation |

States are monotonically advancing. A note cannot move backward (except via explicit human rollback with a documented reason).

## Canonicality Scoring

| Score | Label | Requirements |
|---|---|---|
| 1 | Speculative | Raw agent hypothesis. No validation. Not promoted. |
| 2 | Useful | Useful context. Not fully validated. May be promoted to L3 only. |
| 3 | Validated | Cross-referenced, fact-checked, consistent with other canonical notes. Human review recommended. |
| 4 | Operational Truth | Actively drives decisions. Human approval required. |
| 5 | Doctrine | Foundational, long-lived institutional knowledge. Human approval required. |

Only notes with canonicality ≥ 3 are eligible for Layer 1 promotion.

## Summary Field Standards

The `summary` field is the most important field for retrieval quality. Rules:

1. One sentence only. Hard limit: 150 characters.
2. Written as a declarative statement, not a description of the note.
3. Must contain the key concept, entity, or decision.
4. Must be self-contained — readable without context.
5. Must not begin with "This note..." or "A note about..."

**Good summary examples:**
- `"The vault uses a four-layer memory architecture separating raw archive, canonical knowledge, operational memory, and execution artifacts."`
- `"ADR-001: The Git branch strategy isolates agent writes from canonical main to prevent corruption."`
- `"SOPs for agent handoffs require a structured snapshot including current state, blockers, and next action."`

**Bad summary examples:**
- `"Notes about the memory architecture"` (too vague)
- `"This document describes how the vault works"` (meta-description, not content)
- `"Memory architecture notes, written 2026-05-13, by Builder agent"` (administrative, not knowledge)

## Provenance Rules

Every canonical note must trace to at least one source:

| Source value | Meaning |
|---|---|
| URL | External article, documentation, research |
| `agent_name` | Generated by a specific agent (include agent field) |
| `meeting` | Emerged from a meeting or conversation |
| `import` | Imported from external system |
| `human` | Directly authored by the human founder |
| `transcript:filename.md` | Distilled from a raw transcript |

When distilled from a transcript, include both `source: transcript:filename.md` and `distilled_from: path/to/raw/file.md`.

## Naming Conventions

### File Names

- Lowercase only
- Hyphens only (no underscores, no spaces)
- Descriptive, not date-prefixed for canonical notes
- Agent outputs: `YYYY-MM-DD-HHMM-{task-slug}.md`
- Canonical notes: `{concept-or-decision-slug}.md`

**Good:** `transformer-attention-mechanism.md`, `adr-001-git-branch-strategy.md`
**Bad:** `Note 2026-05-13.md`, `agent_output_final.md`, `DRAFT concept.md`

### ADR Naming

```
adr-{NNN}-{decision-slug}.md
```

Example: `adr-001-git-branch-strategy.md`, `adr-012-embedding-model-selection.md`

### SOP Naming

```
sop-{domain}-{action-slug}.md
```

Example: `sop-vault-transcript-ingestion.md`, `sop-agent-onboarding.md`

## Conflict and Supersession Model

### When to set `contested: true`

Set when a note makes claims that directly contradict one or more existing canonical notes at Tier 3 or above.

**Process:**
1. Curator detects contradiction during promotion or lint
2. Both notes get `contested: true`
3. Both notes get each other's ID in `contradictions: []`
4. A conflict file is created: `09_System/conflicts/YYYY-MM-DD-{slug}.md`
5. Human resolves; loser gets `status: archived` and `superseded_by: {winner_id}`
6. Winner gets `contested: false`, `contradictions: []` cleared

### Supersession Model

When a note is replaced by a newer, better version:

- Old note: `superseded_by: knw-YYYYMMDD-NNNNN`, `status: archived`
- New note: `supersedes: knw-YYYYMMDD-NNNNN`
- Old note is NOT deleted — preserved in Git and in `07_Archive/Knowledge/`
- The supersession chain is browsable

## Review Scheduling

Notes with `review_after: YYYY-MM-DD` are flagged by the daily lint when that date passes.

Default review intervals:

| Note type | Review interval |
|---|---|
| Operational memory | 30 days |
| Project-scoped strategy | 90 days |
| Canonical concepts | 180 days |
| Doctrine (canonicality 5) | 365 days |

On review: either extend the date, update the content, or archive the note.

## Schema Evolution Rules

| Change type | Version bump | Migration required |
|---|---|---|
| New optional field | Minor (2.0 → 2.1) | No — absent = default |
| New required field | Major (2.x → 3.0) | Yes — migration script + batch update |
| Rename existing field | Major | Yes — keep old as alias for 30d, then remove |
| Remove field | Major | Yes — remove from all notes, update all tooling |
| Change allowed values for a field | Minor | Yes — update all affected notes |

Schema version is stored in each note's `schema_version` field and in this file's header.

Before any schema change:
1. Document the change and rationale here
2. Update validation scripts
3. Run migration against test copy of vault
4. Apply to vault
5. Git commit with message: `refactor(system): schema migration 2.0 → 2.1 — {reason}`

## Validation Rules

The pre-commit hook and daily lint check enforce:

1. All required fields present on `canonical: true` notes
2. `id:` matches format `knw-YYYYMMDD-NNNNN`
3. `id:` is unique across the entire vault
4. `id:` has not changed since last commit (immutability)
5. `canonicality:` is 3, 4, or 5 on promoted notes
6. `status: promoted` only when `canonical: true`
7. `summary:` is ≤ 150 characters
8. `created:` and `updated:` are valid ISO dates
9. `ttl:` is present on all Layer 2 operational notes
10. No note in `04_Knowledge/`, `08_Memory/Institutional/`, or `06_Operations/SOPs/` has `canonical: false`

---

## Anti-Patterns

Do not do the following:

- Setting `canonical: true` on unreviewed agent outputs
- Using free-form tag values not in the taxonomy
- Writing summaries that describe the note rather than assert the knowledge
- Assigning `canonicality: 4` or `5` without explicit human approval
- Using the same `id:` for two different notes
- Leaving `review_after:` blank on operational memory
- Creating a note without a `summary:` field
- Using underscores in file names
- Using date-prefixed names for canonical knowledge notes
